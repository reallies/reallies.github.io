추천 카드에 별 입력을 추가하는 안을 다시 검토했다. 이번에는 ‘별점이 없다’는 관찰에서 곧바로 개선안을 고르지 않고, 실제 입력 위치와 대안별 손익을 비교했다. 기존 문제 선택 기록은 이력으로 보존한다. 이 글은 새 기능의 효과를 검증한 결과가 아니다.

## 실제 화면에서 입력 위치 확인

![작품 상세의 예상·평균 별점과 입력용 별](/analysis/watchapedia/observed-detail-20261106.png)

2026년 11월 6일 로그인 상세를 다시 캡처했다. 예상 3.4와 평균 2.9 아래에 입력용 별이 있다. 10월 27일 기록의 예상값은 3.5였다. 두 숫자는 예상과 집계이며 사용자가 남긴 별점이 아니다. 별을 누르지 않아 제출 중·성공·실패와 추가 확인 유무는 관찰하지 않았다. [^F2-S03][^R-W03]

![추천 카드 일부. 예상값·제목·더보기 표시](/analysis/watchapedia/observed-card-20261106.png)

11월 6일 추천 카드와 더보기 메뉴도 재캡처했다. 사용자 이름이 들어간 섹션 제목과 타인의 코멘트는 제외했다. 메뉴에는 보고싶어요·보는 중·코멘트 작성·컬렉션에 추가·관심없어요가 있고 별 입력은 없다. 메뉴를 열고 닫았으며 평가나 상태 변경은 하지 않았다. [^R-W03]

![추천 카드의 실제 더보기 메뉴](/analysis/watchapedia/observed-menu-20261106.png)

평가 전용 목록에는 작품 옆에 빈 별이 있었다. 같은 서비스라도 평가 목록은 별 선택을 앞에 두고, 추천 카드는 후보 정보와 예상값을 보여준다. 이는 입력 위치가 과업에 따라 달라지는 사례로 읽을 수 있다. 실제 제작 의도나 사용자의 선호를 확인한 것은 아니다. [^F1-S02]

## 기능의 부재와 사용자 문제는 다르다

| 확인한 것 | 아직 확인하지 않은 것 |
|---|---|
| 평가 목록과 작품 상세에 별 입력이 있음 | 추천 중 이미 본 작품을 평가하려는 수요·빈도 |
| 수집 당시 추천 카드 메뉴에 별 입력이 관찰되지 않음 | 그 이유로 평가를 포기했는지 |
| 추천 카드에서 작품 상세로 갈 수 있음 | 제출 후 복귀 위치, 저장 방식과 오류 처리 |
| 예상·평균·내 평가 라벨은 서로 다른 정보임 | 새 입력으로 평가량이나 추천 품질이 좋아지는지 |

대표 과업은 ‘추천 목록에서 이미 본 작품을 발견했을 때 별점 하나를 고르기’로 설정했다. 사용자 조사에서 확인한 대표 행동이 아니라 대안을 같은 기준으로 비교하기 위한 가정이다. 이 수요가 없다면 추천 카드에 입력을 늘릴 이유부터 다시 봐야 한다.

## 메뉴를 넣어도 입력 횟수는 줄지 않는다

세 안에서 세는 단위는 클릭이나 탭 한 번이다. 시작점은 추천 목록에서 작품 카드가 보이는 상태이며, 끝은 원하는 별 하나를 고르는 시점이다. 작품을 찾기 위한 스크롤·저장·추가 확인은 이 횟수에 포함하지 않았다. 현행 별 선택은 실행하지 않았으므로 아래 숫자는 경로를 풀어 센 값이며 실제 완료 실험의 측정치가 아니다.

| 안 | 선택 경로 | 별 선택까지 | 얻는 것과 확인할 것 |
|---|---|---|---|
| A · 현행 상세 | 카드 열기 → 상세의 별 선택 | 경로상 2회 | 작품 정보를 보고 평가. 목록 이탈과 복귀 상태는 확인 필요 |
| B · 메뉴 안에 별 | 더보기 열기 → 그 메뉴의 별 선택 | 가정상 2회 | 목록 맥락 유지 가설. 별 입력을 발견하는지 확인 필요 |
| C · 카드 안에 별 | 카드의 별 선택 | 가정상 1회 | 입력이 바로 보임. 오입력과 탐색 정보의 간섭 확인 필요 |

B는 더보기에 ‘평가하기’ 버튼을 넣고 별도 입력창을 여는 방식이 아니다. 메뉴 안에서 별 값을 직접 고르는 안이다. 별도 창을 연다면 단계가 늘 수 있으므로 다시 세어야 한다.

A와 B는 숫자가 같아도 화면을 떠나는지, 작품 정보를 더 보는지, 입력을 쉽게 찾는지가 다르다. C도 한 번이라는 이유만으로 우선할 수 없다. 작품을 둘러보는 중 실수로 별을 고르는 상황과 카드가 복잡해지는 비용을 함께 봐야 한다. 내부 구현 구조를 확인하지 않았으므로 개발 난이도 순위는 매기지 않았다.

## 적용 도식: 선택 위치를 나란히 비교

![상세·메뉴·카드의 별 선택 경로 비교](/analysis/watchapedia/rating-options.svg)

가상 작품과 동일한 입력 과업을 놓은 정적 도식이다. 세 안은 별 선택 이후의 저장·취소·실패 처리를 구현하지 않았다. 이를 포함해 완료를 비교하려면 저장 방식을 통일하거나 차이를 밝힌 뒤 전체 단계를 다시 세어야 한다.

이전 메뉴 중심 가상안은 비교 대안 B로 남기고 최종 개선안으로 확정하지 않는다. 현행 상세 경로를 유지할 수도 있다. 사용자가 이미 본 작품을 추천에서 평가하려는지, 상세 정보 없이도 평가하려는지부터 확인한 뒤 도입 여부를 판단한다.

## 어떤 관찰로 선택할까

먼저 사용자가 추천을 둘러보는 과정에서 이미 본 작품을 어떻게 처리하는지 본다. 평가하려는 행동이 나왔는지, 작품 정보를 더 읽는지, 다른 목록으로 옮기는지를 기록한다. 기능을 써 보라고 지시한 테스트만으로 자발적인 수요를 입증하지 않는다.

이후 같은 작품·정보·저장 조건으로 A·B·C를 비교한다. 평가 입력을 찾는 과정, 선택까지의 시간, 오입력과 수정, 목록 복귀를 본다. 별 선택과 서버 제출 완료는 별도 시점으로 기록한다. 평가량과 추천 만족도도 구분한다. 사용자 테스트와 실제 제출 관찰은 아직 수행하지 않았다.

## 평균·예상·내 평가를 구별하는 표시

과거 로그인 상세에는 예상 3.5와 평균 2.9, 평가 입력 별이 있었다. 홈 카드는 예상·평가함·평균 라벨을 사용했다. 현재 비로그인 상세에서는 평균만 확인했다. [^F1-S01][^F2-S03][^R-W01][^F1-S02]

사용자가 다른 사람의 집계, 자신에 대한 예측, 자신이 남긴 평가를 구별해야 숫자를 올바른 판단 근거로 쓸 수 있다. 평균으로 바뀐 정확한 시스템 조건은 미확인이다.

<div class="dgm"><ol><li>집단의 평가</li><li>평균</li></ol><ol><li>개인화 예측</li><li>예상</li></ol><ol><li>내가 제출한 값</li><li>내 평가</li></ol></div>

별이라는 같은 시각 표현을 써도 정보의 생산자가 다르다. 출처 라벨과 입력 상태를 구분하는 목적은 예상값과 내 기록의 혼동을 줄이는 데 있다. 실제로 구별하는지는 사용자에게 확인해야 한다.

### 대안과 적용 조건
예상값만 강조하면 선택을 단순하게 만들 수 있으나 집계와의 차이를 숨긴다. 세 값을 모두 동일한 무게로 보여주면 혼잡할 수 있어 과업별 우선순위와 명확한 라벨을 함께 검토한다.

예측·집계·개인 기록이 공존할 때 적용한다. 예상값 미생성 사유와 계산 방법은 확인 없이 만들어 쓰지 않는다. 가상 제출 상태는 현행 구현과 구분한다.

### 확인할 질문
각 숫자가 누구의 판단인지 설명하는가? 제출 성공 후 자신의 값과 예측값을 구별하는가? 예상값과 다른 평가를 했다는 사실만으로 평가의 진정성을 판정하지 않는다.

## 취향 추천과 감상 가능한 곳을 따로 확인하는 이유

추천에는 OTT 선택과 구독중 작품 토글이 관찰됐다. 상세에는 구독·대여·소장 경로가 나뉘고 현재 공개 상세도 제공처 정보의 최신성을 보증하지 않는다고 안내한다. [^F1-S04][^F2-S04][^R-W02][^F2-S05]

마음에 드는 후보인지 판단하는 일과 자신의 구독·지역·계정 조건으로 감상할 수 있는지 확인하는 일은 다르다. 서비스 배지가 있다는 사실만으로 즉시 재생 가능한 것은 아니다.

<div class="dgm"><ol><li>취향 후보</li><li>제공처·이용 방식 확인</li><li>외부 플랫폼</li><li>계정별 조건 확인</li><li>감상</li></ol></div>

예상 별점은 선호 판단을, OTT·가격·구독/대여/소장은 접근 조건 판단을 돕는다. 예상 별점 옆에 제공처와 이용 방식을 따로 표시하면 취향과 접근 조건을 각각 확인할 수 있다.

### 대안과 적용 조건
구독 가능작만 먼저 거르면 접근은 쉬울 수 있으나 후보 폭이 줄어든다. 전체 후보에 제공처를 표시하면 선택 폭은 유지되지만 확인 부담이 남는다. 사용자의 발견/즉시감상 과업에 맞춰 선택한다.

제공처 데이터의 갱신 시점과 계정별 조건의 한계를 알릴 수 있을 때 적용한다. 설정 저장·토글을 재현하지 않았으므로 필터 결함과 선택값의 실제 적용 규칙을 확정하지 않는다.

### 확인할 질문
사용자가 취향 적합성과 접근 조건을 각각 설명하는가? 외부 서비스에 가서 다른 조건을 만났을 때 돌아올 수 있는가? 제공처 클릭과 실제 재생·구독 성공을 구별한다.
