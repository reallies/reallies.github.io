관찰한 화면 구조로 과업과 설계 대안을 해석한 글이다. 제작 의도, 사용자 수요, 효과는 확인하지 않았고 아래 검증 질문은 모두 실행 전이다. 단계 도식은 화면 관계를 설명하려고 재구성한 것으로 실제 전체 흐름이 아니다.

## 평가 목록과 추천 목록의 정보가 다른 이유

로그인 홈에는 평가·취향분석·추천 진입점이 따로 있다. 평가 목록은 별 입력에, 취향분석은 분포·선호 설명에, 추천은 후보와 이유에 공간을 쓴다. [^F1-S01][^F1-S02][^F1-S03][^F1-S04]

이미 본 작품을 기억해 기록하는 일과 아직 보지 않은 작품을 고르는 일은 필요한 정보가 다르다. 기록에서 추천으로 바로 이동하려는 수요는 관찰하지 않았다.

<div class="dgm"><p>기록</p><ol><li>본 작품 기록</li><li>취향의 요약</li></ol><p>발견</p><ol><li>다음 후보 발견</li><li>작품 상세</li><li>감상 경로</li></ol></div>

기록에는 입력 대상을 빠르게 알아보는 제목과 별이, 추천에는 판단을 돕는 예상값·이유가 배치된다. 평가 목록은 감상 기록에, 추천 목록은 후보 선택에 필요한 정보를 앞에 둔 구성으로 읽을 수 있다. 평가수가 많다는 사실만으로 추천이 정확해졌다고 결론 내릴 수 없다.

### 대안과 적용 조건
한 화면에 기록과 추천을 합치면 이동은 줄지만 본 작품과 볼 작품, 내 평가와 예상값을 혼동할 수 있다. 과업별 화면은 집중에 유리하나 전환 과업이 실제로 있는지 확인하고 연결을 설계해야 한다.

이력 기록과 미래 선택을 함께 다루는 영화·독서 서비스에 적용한다. 모든 화면에 다음 행동 버튼을 넣는 것이 정답이라는 전제는 두지 않는다.

### 확인할 질문
사용자가 평가 화면과 추천 화면을 구별하고 원하는 과업으로 이동하는가? 과업 전환이 필요한 상황을 실제 이용 연구에서 먼저 확인한다.

## 평균·예상·내 평가를 구별하는 표시

과거 로그인 상세에는 예상 3.5와 평균 2.9, 평가 입력 별이 있었다. 홈 카드는 예상·평가함·평균 라벨을 사용했다. 현재 비로그인 상세에서는 평균만 확인했다. [^F1-S01][^F2-S03][^R-W01][^F1-S02]

사용자가 다른 사람의 집계, 자신에 대한 예측, 자신이 남긴 평가를 구별해야 숫자를 올바른 판단 근거로 쓸 수 있다. 평균으로 바뀐 정확한 시스템 조건은 미확인이다.

<div class="dgm"><ol><li>집단의 평가</li><li>평균</li></ol><ol><li>개인화 예측</li><li>예상</li></ol><ol><li>내가 제출한 값</li><li>내 평가</li></ol></div>

별이라는 같은 시각 표현을 써도 정보의 생산자가 다르다. 출처 라벨과 입력 상태를 구분하는 목적은 예상값과 내 기록의 혼동을 줄이는 데 있다. 실제로 구별하는지는 사용자에게 확인해야 한다.

### 대안과 적용 조건
예상값만 강조하면 선택을 단순하게 만들 수 있으나 집계와의 차이를 숨긴다. 세 값을 모두 동일한 무게로 보여주면 혼잡할 수 있어 과업별 우선순위와 명확한 라벨을 함께 검토한다.

예측·집계·개인 기록이 공존할 때 적용한다. 예상값 미생성 사유와 계산 방법은 확인 없이 만들어 쓰지 않는다. 가상 제출 상태는 현행 구현과 구분한다.

### 확인할 질문
각 숫자가 누구의 판단인지 설명하는가? 제출 성공 후 자신의 값과 예측값을 구별하는가? 예상값과 다른 평가를 했다는 사실만으로 평가의 진정성을 판정하지 않는다.

## 별점 입력은 카드·메뉴·상세 중 어디에 둘까

과거 평가 목록에는 카드 별 입력이 있고 추천 카드에는 상세 링크와 더보기(⋮)가 있다. 추천 메뉴에는 보고싶어요·보는 중·코멘트·컬렉션·관심없어요가 관찰됐고 별 입력은 없었다. [^F1-S02][^F1-S04][^F2-S03]

추천을 보다가 이미 본 작품을 평가하려는 상황은 가능한 시나리오지만 실제 수요와 빈도는 확인하지 않았다. 카드에 기능이 없다는 사실만으로 과업 실패를 주장할 수 없다.

<div class="dgm"><p>현행 관찰</p><ol><li>추천 카드</li><li>상세</li><li>별 선택</li></ol><p>대안 가정 1</p><ol><li>카드 메뉴</li><li>별 선택</li></ol><p>대안 가정 2</p><ol><li>카드 안의 별 선택</li></ol></div>

메뉴에 별점을 넣으면 목록 안에서 평가할 수 있다. 사용자가 메뉴 속 기능을 찾는지는 확인해야 한다. 상세 진입 후 별 선택과 메뉴 후 별 선택은 모두 2회 입력이므로 클릭 감소로 우위를 설명하면 안 된다. 카드에 별을 직접 두는 안은 입력 진입을 줄이는 대신 탐색 중 오입력과 카드 복잡도를 확인해야 한다.

### 대안과 적용 조건
상세는 정보 확인과 평가를 함께 지원한다. 메뉴는 선택적 행동을 수용한다. 카드 직접 입력은 반복 평가가 주 과업일 때 후보가 된다. 세 대안의 개발 난이도는 내부 구조를 보지 않았으므로 순위를 매기지 않는다.

이미 본 작품을 평가하려는 실제 수요가 확인되면 대안을 비교한다. 수요가 없거나 실수 비용이 큰 경우 기존 상세 경로를 유지하는 안도 포함한다.

### 확인할 질문
평가 진입 발견률·완료시간·입력 오류·정정 가능성·원래 목록 복귀를 같은 과업과 동일한 횟수 기준으로 비교한다. 평가량 증가만으로 추천 품질 향상을 주장하지 않는다.

## 취향 추천과 감상 가능한 곳을 따로 확인하는 이유

추천에는 OTT 선택과 구독중 작품 토글이 관찰됐다. 상세에는 구독·대여·소장 경로가 나뉘고 현재 공개 상세도 제공처 정보의 최신성을 보증하지 않는다고 안내한다. [^F1-S04][^F2-S04][^R-W02][^F2-S05]

마음에 드는 후보인지 판단하는 일과 자신의 구독·지역·계정 조건으로 감상할 수 있는지 확인하는 일은 다르다. 서비스 배지가 있다는 사실만으로 즉시 재생 가능한 것은 아니다.

<div class="dgm"><ol><li>취향 후보</li><li>제공처·이용 방식 확인</li><li>외부 플랫폼</li><li>계정별 조건 확인</li><li>감상</li></ol></div>

예상 별점은 선호 판단을, OTT·가격·구독/대여/소장은 접근 조건 판단을 돕는다. 예상 별점 옆에 제공처와 이용 방식을 따로 표시하면 취향과 접근 조건을 각각 확인할 수 있다.

### 대안과 적용 조건
구독 가능작만 먼저 거르면 접근은 쉬울 수 있으나 후보 폭이 줄어든다. 전체 후보에 제공처를 표시하면 선택 폭은 유지되지만 확인 부담이 남는다. 사용자의 발견/즉시감상 과업에 맞춰 선택한다.

제공처 데이터의 갱신 시점과 계정별 조건의 한계를 알릴 수 있을 때 적용한다. 설정 저장·토글을 재현하지 않았으므로 필터 결함과 선택값의 실제 적용 규칙을 확정하지 않는다.

### 확인할 질문
사용자가 취향 적합성과 접근 조건을 각각 설명하는가? 외부 서비스에 가서 다른 조건을 만났을 때 돌아올 수 있는가? 제공처 클릭과 실제 재생·구독 성공을 구별한다.

## 패턴 선택표

네 원리의 적용 조건을 비교한다.

| 패턴 | 과업·구조 | 대안 | 배제 기준 |
|---|---|---|---|
| 기록·발견 분리 | 본 작품 입력과 볼 작품 선택의 과업을 구분 | 분리 화면/통합 목록 | 전환 수요 없이 모든 화면에 CTA 추가하지 않음 |
| 평가 출처 라벨 | 평균·예상·내 평가를 구별 | 주정보+보조설명/동시비교 | 미확인 예측 생성 규칙 단정 금지 |
| 과업별 행동 배치 | 상세/메뉴/직접입력을 동일 과업으로 비교 | 현행상세/메뉴/직접별 | 수요·빈도 없이 카드별점 추가 확정 금지 |
| 취향·접근 조건 분리 | 예상값과 제공처·이용방식을 구분 | 전체후보+배지/가능작필터 | 배지만으로 재생 가능 보장 금지 |

## 가상 적용: 작품 발견과 감상 기록

왓챠피디아 개편안이 아니라, 콘텐츠 서비스에서 기록과 발견의 과업을 나눠 패턴을 적용해 본 연습이다.

대상은 감상 후보를 고르거나 이미 본 작품을 기록하려는 사용자. 두 과업의 발생 빈도는 가정하지 않는다. 추천 카드에서 평가하려는 실제 수요부터 확인한다.

### IA와 패턴 대응
발견 목록(예상·추천 이유·제공처) → 작품 상세(정보·평가·접근 조건).
기록 목록(작품 식별·내 평가 입력) → 내 기록/취향 요약.
평균·예상·내 평가는 출처를 유지한다. 제공처는 접근 조건이며 취향 점수와 별도 축이다.

### 화면 1. 발견 목록과 대안 비교

![화면 1. 발견 목록](/analysis/watchapedia/wireframe-1.svg)

평가 진입은 세 대안을 비교한다: A 상세→별 선택(기준안), B 더보기→별 선택(문맥 유지 가설), C 카드 직접 별(발견성/오입력 비교). B를 클릭 절감안이라 부르지 않는다. 모든 안에서 보고싶어요와 평가의 의미를 분리한다. 이미 본 작품을 평가하려는 수요가 없으면 A 유지가 가능하다.

### 화면 2. 평가 입력과 상태

![화면 2. 평가 입력과 상태](/analysis/watchapedia/wireframe-2.svg)

본 가상안은 별 선택 후 저장으로 제출을 분리한다. 관찰 기록에는 별 클릭이 제출 진입 동작으로 기재됐지만 실제 제출 단계와 추가 확인 유무는 미확인이다. 따라서 대안 비교 시 모든 시안의 입력 횟수를 실제로 다시 센다. 미선택은 저장 불가, 선택중은 미저장 표시, 제출중은 중복 제출 방지, 성공은 내 평가값 확인, 실패는 입력 보존+재시도+취소를 제공한다. 수정은 이전값을 보존하고 삭제는 되돌릴 방법 또는 명확한 확인을 설계한다. 서버 반영과 클라이언트 낙관 표시를 구분해야 하며 본 문서는 구현 완료 기록이 아니다.

### 화면 3. 감상 경로

![화면 3. 감상 경로](/analysis/watchapedia/wireframe-3.svg)

취향 점수와 감상 가능 조건을 함께 보여주되 같은 의미로 합치지 않는다. 제공처 데이터가 없거나 오래되면 모름/확인필요로 표시한다. 외부 이동 실패 시 상세 복귀와 다른 제공처 탐색을 제공한다. 구독 가입·결제·재생은 이 시안 범위 밖이다.

## 검증 계획

먼저 실제 추천 탐색 중 이미 본 작품을 인지하고 평가하려는 수요가 발생하는지 관찰·인터뷰한다. 없다면 카드 평가안의 필요성을 재검토한다. 평가 수를 늘리는 목표만으로 기능 추가를 정당화하지 않는다.

같은 작품·과업·정보로 현행 상세, 메뉴, 카드 직접 입력을 비교한다. 입력 단계와 저장 방식을 통일하거나 차이를 명시하고 클릭수를 다시 센다. 발견률·완료시간·오입력·취소·정정·목록 복귀를 본다. 사전 파일럿으로 판정 기준을 고정하며 현재 표본 수·효과 크기는 미설정이다.

평균·예상·내 평가의 출처를 말하도록 하여 혼동을 확인한다. 예측과 다른 평가를 정직성의 증거로 삼지 않는다. 자기선택·기억·예측 노출의 영향을 분리해 다룬다.

제공처 과업은 구독/대여/소장을 구분하고 외부 조건 확인으로 이동할 수 있는지 본다. 외부 클릭은 재생 성공이 아니다. 계정별 실제 권한 확인은 별도 승인 범위다.

추천 품질은 평가량과 별도로 정의해야 한다. 유효한 후보 발견·선택 만족 등 과업 지표와 반복 사용의 의미를 검토하고, 로그·동의·개인정보 요건 및 필요한 관측기간을 정한 후 실행한다. 공개 누적카운터를 기준선으로 쓰지 않는다. 유의하지 않은 결과가 효과 없음을 뜻하지는 않으며 추정 범위와 검정력을 함께 해석한다.
