# 댕냥여지도 — 반려동물 동반시설 검색 + 행동 분석

> **반려동물 조건 기반 탐색을 팀과 구체화하고, 퍼널과 대시보드를 맡은 서브리드 · 주 개발(풀스택)**

## 문제

반려동물 동반 시설을 찾을 때 ① 검색→상세 진입에서 이탈이 크고(전환 병목), ② 동반 조건이 상단에 드러나지 않아 같은 시설을 반복 조회하게 된다. "어디서, 왜 이탈하는가"를 데이터로 보이게 만드는 것이 과제였다.

팀 브레인스토밍에서 먼저 **반려동물**이라는 테마를 정했다. 이후 조사는 그 테마 안에서 어떤 문제를 풀고 어떤 탐색 구조를 만들지 좁히는 데 사용했다.

## 조사·기획

사전조사 문서 **「주제 선정 이유 + 자료조사」**를 작성했다. 자료는 시장 규모, 문제 사례, 사용자 페르소나, 시장조사 요약의 네 부분으로 구성했다.

시장 규모에는 KB금융 2025 반려동물 보고서와 농식품부 2024 양육 실태조사를 인용했다. 반려인 1,546만 명이라는 외부 자료도 함께 정리했다. 이 수치는 시장을 설명하는 조사 자료로만 사용했다.

보도 사례와 공공 데이터 설명에서는 네 가지 문제를 모았다. 안내와 달리 현장에서 입장을 거부당하는 정보 불일치, 동반 가능한 식당 부족, 시설별 입장 조건의 불투명함, 공공 데이터의 한계였다.

사용 상황을 구체화하려고 사용자 페르소나 3명을 만들었다. 이어 시장 기회·핵심 문제·기회 공백·서비스 방향을 한 표로 정리했다.

조사에서 잡은 기회 공백은 명확했다. 공공 데이터는 부정확하고 부분적이며, 민간 서비스는 조건 필터링을 지원하지 않았다. 그래서 체중·견종 같은 내 반려동물 조건으로 실제 입장 가능한 시설을 찾는 방향을 검토했다.

## 내린 결정

3월 8일 팀 회의에서 **조건 기반 탐색 구조를 MVP 범위에 넣는 것**으로 합의했다. 조사에서 좁힌 방향은 이 팀 합의로 이어졌다.

측정에서는 사용자 행동을 5단 퍼널로 정의했다.

`검색 → 상세 → 조건확인 → 방문의향 → 재방문`

단계별 전환율 외에 루프 완주율과 재사용 지수를 수식으로 설계했다. 루프 완주율은 검색한 사람 중 방문의향 행동까지 간 비율로 정의했다. 재사용 지수는 사용자당 평균 루프 반복 횟수로 두었다.

검증 기준으로 아래 목표값도 정했다.

- 검색→상세 ≥25%
- 상세→조건확인 ≥50%
- 조건확인→방문의향 ≥30%
- 재탐색률 ≤40%
- 루프 완주율 ≥0.5
- 재사용 지수 ≥0.3
- 이벤트 수집률 ≥95%

이 값들은 실제 달성 수치가 아니라 설계 단계에서 정한 **목표값**이다.

## 직접 만든 것

### 데이터 분석

- **퍼널 분석 지표 정의**: 단계별 전환율과 재탐색률·루프 완주율·재사용 지수를 정의했다.
- **Streamlit 분석 대시보드**: pandas와 Plotly로 퍼널·전환율·재탐색률·루프 완주율을 시각화했다. `streamlit_app.py`로 구현했다.
- 대시보드에 사용한 수치는 샘플 데이터이며 실제 서비스 실측값으로 해석하지 않았다.
- 이벤트 스키마와 SQL 분석 쿼리는 분석을 맡은 팀원이 작성했다. 대시보드는 그 구조에서 산출되는 값을 확인할 수 있게 만들었다.

### 프론트엔드

React·Vite·TypeScript 모노레포에서 화면 구현을 맡았다. 구조는 `apps/web`·`apps/api`·`packages/shared`로 나뉘었다.

구현 화면은 home, main(검색), detail(+review), saved(저장)였다.

### 기술 스택

| 구분 | 기술 |
| --- | --- |
| 데이터 분석 | **Python · Streamlit · pandas · Plotly · MySQL 8(SQL 분석 쿼리)** |
| Frontend | **React · Vite · TypeScript** (모노레포) |
| 데이터 모델 | event_logs 중심 이벤트 스키마 |

## 결과

사전조사에서 정리한 조건 기반 탐색 방향이 3월 8일 회의에서 MVP 범위에 포함됐다. 이후 사용자 행동을 5단 퍼널로 정의하고 측정 기준을 수식과 목표값으로 구체화했다.

퍼널·전환율·재탐색률·루프 완주율을 확인할 수 있는 Streamlit 대시보드를 구현했다.

프론트에서는 검색·상세·리뷰·저장 화면을 구현했다.

## 배운 점

데이터로 의사결정을 하려면 "지표를 정의"하는 것만으로는 부족하고, **그 지표가 실제로 산출되도록 로깅 스키마부터 쿼리·대시보드까지 이어져야** 한다는 것을 대시보드를 맡아 체감했다.
